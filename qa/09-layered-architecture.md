# Q9. レイヤードアーキテクチャ

## 問題

Controller / Service / Repository の役割を説明してください。

また、以下も答えてください：

- なぜ分離するのか
- ControllerとServiceの責務の境界

## 回答

ブラウザからのリクエストは、初めにControllerを通ります。Controllerは、そのリクエストが様式に沿っているかどうかを確かめ、その内容の処理をServiceに渡します。

Serviceは、決まったルールを持っていて、それを元に内容が合っているかどうかを考え、処理をします。その際に必要なデータの取得や変更等はRepositoryに頼み、Repositoryがデータベースと通信します。レスポンスはその逆をたどり、Controllerからブラウザへと返っていきます。

この3つに分離する理由は、3つあります。1つ目は、エラーが起きた場所が分かりやすいことです。2つ目は、1つずつテストができることです。3つ目は、それぞれの役割を明確に持たせることができ、正しいルールをServiceが持つため、確認の漏れが出なくて済むことです。

ControllerとServiceの責務の境界は、リクエストの様式を見るか、内容を見るかです。Controllerは、リクエストが様式に沿っているかどうかまでしか見ません。Serviceは、Controllerから来たリクエストの内容が合っているかどうかを、データベースからの情報等を用いて吟味します。例えば、パスワードやユーザー名に決められた文字が含まれているか、決められた文字数以内かを見るのが様式の確認です。さらに、その中身が他のユーザーと重複していないかなどを見るのが、ルールの確認です。

## 理解のメモ

- たとえ：レストラン。ホール係（Controller）が注文を聞き、料理人（Service）に伝える。料理人は、食材係（Repository）に冷蔵庫（DB）から食材を持ってきてもらう。できた料理はホール係が運ぶ。
- Controller ＝ 個数の欄に「あああ」と書いてあれば断る（様式）。紙を見るだけで分かる。Service ＝ 卵アレルギーの人のオムライスを断る（ルール）。リクエスト通りにやることが絶対ではない。
- Controller / Service / Repository はツールではなく、バックエンドのプログラムの役割の名前。開発者がコードを書いて作る。別々のサーバーではなく、1つのバックエンドの中でファイルを分けたもの。ツールは Spring Boot や MyBatis。DB は Repository の中身ではなく、別にある。
- 3つは最初から備わっているものではない。Controller に全部書いても動くが、分けたほうがよいので、開発者が分けて作る。
- クラスに名札（アノテーション）を付けると、その役割として扱われる。`@RestController`・`@Service` は Spring、`@Mapper` は MyBatis が用意したもので、開発者は `import` して付けるだけ。クラス名だけでは Controller にならない。名札は役割を宣言するだけで、中身を役割どおりに書くのは開発者。
- 投稿の削除の流れ：`PostController.delete`（受け取って渡す・204 を返す）→ `PostCommandService.delete`（自分の投稿か確かめる）→ `PostMapper.softDelete` と `PostMapper.xml`（SQL を実行する）→ DB。
- 様式（形式）＝ 届いたデータの書き方の決まり。「書き方が正しいか」。ルール（ビジネスルール）＝ アプリの決まりごと。「書き方は正しいけれど、認めてよいか」。
- ユーザー登録の例：ユーザー名が `あ` なら様式で断る（3〜20文字の半角英数字と `_`）。`admin` は様式は正しいが、予約語なのでルールで断る。使用済みの `hanako` も、重複なのでルールで断る。形式は `SignupRequest` と `@Valid`、予約語と重複は `AuthCommandService` で確かめている。
- 3つ目の理由：ルールを Service に置くと、入口（Controller）が増えても同じ Service を必ず通るので、確認の漏れが出ない。ルールを Controller に置くと、新しい入口で確認が抜けてしまう。
- 変更にも強い。DB や SQL が変わっても、主に Repository を直せばよい。
- Controller は、JSON の受け取り・返し方やステータスコードなど、HTTP のことを担当する。Service は HTTP のことをなるべく知らないようにする。
- トランザクション（まとめて成功・まとめて取り消し）は、処理のまとまりを知っている Service に付ける（`@Transactional`）。
- 境界はきっちり決まっているわけではない。このアプリでは、投稿の本文の文字数は Service（`PostContent.validate`）で確かめている。「本文か画像のどちらかは必須」のように、本文だけを見ても決まらないルールがあるため。
- このアプリの実装：Repository に当たるものは Mapper（MyBatis）。一覧の `limit` が 1〜50 かどうかは `PostController`、投稿の持ち主が本人かどうかは `PostCommandService` の `findOwn`（Q4）で確かめる。
