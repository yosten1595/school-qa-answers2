# Q14. Flyway（DBマイグレーション）

## 問題

マイグレーションツールを使う理由を説明してください。

（直接ALTER TABLEしない理由）

## 回答

データベースマイグレーションというのは、テーブルの形の変更を記録しながら進めることです。

直接ALTER TABLEを実行すると、個人のPCのデータベースでは変更が起こるものの、チームでプロジェクトを開発している場合、他の人がGitHubから変更のコードを取り込んだとしても、取り込んだ人のデータベースでは変更が行われていないため、うまくいかないことがあります。本番のデータベースでも同じことが起こります。

そのため、Flywayのツールを使って、データベースの変更をファイルにして、コードと一緒にGitHubに置きます。Flywayは、アプリを起動するときに、まだ実行していないファイルを実行してくれます。その際に、データベースごとに人の手でSQLを実行することがないため、入力ミスや実行し忘れを防げます。また、複数の変更があった場合にも、正確な順番で実行してくれるからです。

## 理解のメモ

- ここでのマイグレーションは、システムをクラウドへ移すことではなく、DB マイグレーション（テーブルの形の変更）のこと。
- 例：花子さんが自分の PC の DB に直接 `ALTER TABLE users ADD COLUMN birthday DATE;` を実行し、`birthday` を使うコードを GitHub に上げた。太郎さんがコードを取り込むと、太郎さんの DB には `birthday` 列がないのでエラーになる。本番の RDS も別の DB なので、本番に出すとエラーになる。
- DB は、開発者それぞれの PC と本番で別々にある。Docker で動かす DB も、それぞれの PC の中に1つずつできる。開発で本番の DB を使うと、間違いで利用者のデータを壊してしまう。
- ALTER TABLE を使わないのではない。直接実行せず、`V10__add_birthday_to_users.sql` のようなファイルに書いて、Flyway に実行させる。
- Flyway の流れ：起動するたびに、①この DB でどこまで実行したかの記録（`flyway_schema_history` テーブル）を見る ②まだ実行していないファイルを番号の順に実行する ③実行したことを記録する。だから、どの DB も同じファイルを同じ順番で実行し、同じ形になる。
- 用語：スキーマ ＝ テーブルの形。適用 ＝ ファイルを DB に実行すること。未適用（Pending）・適用済み（Success）。バージョン ＝ `V1`・`V2` などの番号。スキーマ履歴テーブル ＝ どこまで適用したかの記録。まとめると「起動するたびに、スキーマ履歴テーブルを見て、未適用のマイグレーションをバージョンの順に適用する」。この動きを `migrate` と呼ぶ。マイグレーションツールは、スキーマのバージョン管理をする道具。
- 順番が大事な例：V3 で `posts` を作ってから、V8 で `post_images`（投稿の画像）を作る。逆の順番では作れない。
- ファイルは GitHub に残るので、いつ・誰が・なぜテーブルの形を変えたかが後から分かる。
- 実行済みのファイルは書き換えない。直したいときは、新しい番号のファイルを足す（実行済みのファイルを書き換えると、Flyway が記録との違いに気づいてエラーにする）。
- このアプリ：`backend/src/main/resources/db/migration` に `V1__create_users.sql` から `V9__add_user_search_indexes.sql` まで。スキーマを変更するのは Flyway だけ、と決めている（`docs/08_tech_stack.md`）。テストの DB も、本番と同じマイグレーションで作る。
