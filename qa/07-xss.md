# Q7. XSS（クロスサイトスクリプティング）

## 問題

以下について説明してください：

- `<script>alert('攻撃')</script>` が投稿された場合のリスク
- Reactでの対策方法

## 回答

XSSは、開発者が作ったWebアプリのコードに対してスクリプトコードを追加することにより、本来開発者が書いていなくても、ブラウザがそれを命令と読み取り、そのWebアプリを訪れたユーザーのログイン情報を漏洩するなどの被害を与える攻撃になります。

`<script>alert('攻撃')</script>` が投稿された場合は、ユーザーがそのWebアプリを訪れたことにより、ポップアップ表示がされます。ポップアップ表示がされたということは、ブラウザで開いたアプリの画面に第三者が入ってきていて、自由に出入りができてしまうことがわかります。そのため、ログイン情報が盗まれたり、投稿や削除、編集を勝手にされたりする恐れがあります。

Reactでの対策としては、画面に表示する際に、入力されたスクリプトコードの特殊文字を違う文字列に変換し、ブラウザに命令ではなくただの文字列として扱わせる自動エスケープがあります。ただ、`dangerouslySetInnerHTML` を使うとエスケープがされないため、この手段は使わないようにします。どうしても使う場合は、スクリプトコードの部分を削除してしまうサニタイズで対策を取る必要があります。

また、ログイン情報はブラウザのクッキーに保持されているため、第三者にクッキーの中の情報を盗まれないように、HttpOnlyの設定をしておく必要があります。HttpOnlyは、直接クッキーを盗もうとする攻撃に対しては有効ですが、ポップアップ表示や勝手な投稿などをさせるスクリプト攻撃は、自動エスケープやサニタイズで防ぐ必要があります。そのため、XSSの対策は、HttpOnlyだけでは十分ではありません。

## 理解のメモ

- 被害を受けるのは、書いた人ではなく見た人。クリックしなくても、ページを開いただけでスクリプトが動く。
- たとえ：家に帰ると、机の上に「攻撃」と書かれた紙があった。何も盗まれていなくても、誰かが自由に出入りできることが分かる。家がブラウザで開いた画面、紙が `alert` の窓。窓を出すこと自体には、ログイン情報は使われない。
- 秘書（ブラウザ）は、ページに書かれた指示が開発者のものか攻撃者のものか、区別できない。
- 本物の攻撃者は `alert` のような目立つものは使わず、気づかれないように操作や情報の送信をさせる。誘い文句を出して偽のページへ誘導することもある。
- スクリプトは、入力・保存の段階ではただの文字で、動かない。ブラウザが HTML の命令として読んだときに初めて動く。だから React は表示するときにエスケープする（DB には元のまま保存される）。エスケープは隠しているのではなく、動くこと自体を止めている。
- エスケープ ＝ `<` を `&lt;` などに変えて、文字としてそのまま見せる。サニタイズ ＝ 危ない部分を取り除く。太字などを HTML として見せたいときは、エスケープでは太字まで文字になるので、サニタイズを使う。
- 「ただの文字として扱う」という考え方は、Q6 の `#{}` と同じ。
- HttpOnly ＝ JavaScript に Cookie の中身を読ませない設定。スクリプトが動くこと自体は止めない。Cookie はブラウザが自動で付けて送るので、勝手な操作は防げない。XSS を防ぐものではなく、起きたときの被害を減らすもの。
- 「読めない」と「使われない」は別。盗まなくても、本人のブラウザの中から本人として操作できる。たとえ：ロックを解除したスマホを置いて席を外すと、パスワードを知らない人でも、そのスマホから本人として LINE を送れる。
- Cookie を盗むスクリプトは、`document.cookie` で中身を読んで、攻撃者のサーバーへ送る。HttpOnly の Cookie はここに出てこない。勝手に投稿するスクリプトは `document.cookie` を使わず、リクエストを送るだけなので、HttpOnly では止まらない。
- エスケープはスクリプトが動くこと自体を止めるので、どちらの攻撃も防ぐ。HttpOnly は、エスケープに漏れがあったときの備え。
- `innerHTML` で入れた `<script>` は動かないが、`<img src="x" onerror="...">` のような形なら動く。だから `<script>` だけを消しても足りず、サニタイズには専用のライブラリ（DOMPurify など）を使う。
- このアプリの実装：React の標準エスケープを使い、`dangerouslySetInnerHTML` は使わない決まり（NFR-SEC-04）。フロントエンドのコードでも使われていない。アクセストークンとリフレッシュトークンは、どちらも HttpOnly の Cookie に入れている（`AuthCookies`）。
