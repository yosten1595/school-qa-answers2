# Q1. セッション認証とトークン認証

## 問題

「セッション認証」と「トークン（JWT）認証」の違いを説明してください。

また、このアプリでJWTを採用した理由（利点）も述べてください。

## 回答

セッション認証では、ユーザーのアドレスとパスワードをサーバーへ送った際に、そのログイン状態はメモリやデータベースに保持されます。その際に、サーバーはセッションIDを発行し、ユーザーのブラウザに保持させます。よって、第三者がセッションIDを盗んだとしても、サーバーはログイン状態を破棄することによって、第三者が悪用することができないので、セキュリティ面においては強いと言えます。

JWT認証においては、サーバーはあらかじめ用意された秘密鍵とユーザー情報を計算し、署名を作ります。その署名とユーザー情報を組み合わせ、アクセストークンを発行し、ユーザーのブラウザに保持させます。第三者がアクセストークンの中身を書き換えた場合には、第三者からのリクエストがあった際に、サーバーは秘密鍵とアクセストークンの中身から再計算した署名と、アクセストークンについている署名を比べ、整合性を図ります。2つの署名が一致しなければ、サーバーはリクエストを拒否します。

一方、中身がそのまま複製された場合は、署名では見抜けません。そのため、アクセストークンは15分と設定し、有効期限を短くしますが、ユーザビリティが損なわれないためにも、リフレッシュトークンを7日と設定します。リフレッシュトークンはログアウトした際に削除されるため、第三者に盗まれた場合であっても、攻撃を止めることができます。

2つの認証を比べると、ログイン状態の情報が保持されるのがサーバーであるセッション認証と、トークンの中身に保持されるJWT認証であることが違いです。また、ロードバランサーを用いて複数のサーバー環境を作る際には、セッション認証ではリクエストを通すためにログイン状態の情報を引き継いでおく必要があります。JWT認証ではアクセストークンの中身にログイン状態の情報があるので、スムーズにリクエストが通ります。

今回のアプリにおいては、小規模ではありますが、SNSアプリをモチーフにしたものであるため、今後、不特定多数のユーザーの利用が見込まれます。そのため、サーバーを複数用意していくことを考えれば、それに対応しやすいJWT認証を採用した方がいいというところで、JWT認証を採用しました。

## 理解のメモ

- 違いの一言：ログイン状態を、サーバーが覚えておくか（セッション認証）、トークン自身が持つか（JWT認証）。長所・短所はすべてここから出てくる。
- セッションIDやアクセストークンは、ログインのときだけでなく、リクエストのたびにブラウザから送られる。
- セッション認証は、サーバー側でログイン状態を消せば、複製されたセッションIDもすぐに使えなくできる（たとえ：ホテルのフロントがカードキーの登録を消す）。
- 秘密鍵と署名は別のもの。
  - 秘密鍵：開発者があらかじめ用意し、サーバーだけが持つ。全員共通で1つ。トークンには入っていない（たとえ：はんこ）。
  - 署名：トークンを発行するたびに、中身と秘密鍵から計算して作る。トークンの一部（たとえ：印影）。
  - アクセストークン ＝ 中身（ユーザーIDなど）＋ 署名。
- 確かめ方のイメージ：署名 ＝ 中身 × 秘密鍵（実際の HS256 はもっと複雑な計算で、署名から秘密鍵を逆算することもできない）。秘密鍵が 7、中身が 42 なら署名は 294。中身を 99 に書き換えると 99 × 7 ＝ 693 となり、付いている 294 と合わないので拒否される。
- 署名で見抜けるのは「書き換え」。「そっくり複製」は見抜けないので、有効期限を短く（15分）して被害を小さくする。
- ログアウトでリフレッシュトークンを削除しても、複製されたアクセストークンは有効期限（最大15分）まで使えてしまう。止められるのは、リフレッシュトークンを使ったトークンの作り直し。
- リフレッシュトークンを削除できるのは、サーバーが DB（`refresh_tokens`）に保存しているから。このアプリは、アクセストークンは JWT、リフレッシュトークンはセッションに近い方式で、2つのいいとこ取りをしている。
- リフレッシュトークンは JWT ではなく、ただのランダムな値。DB にはハッシュで保存し、届いたら DB で探す（たとえ：クロークの番号札と台帳）。
- アクセストークンの作り直しは、期限が切れて 401 が返ってきたときに、画面側が自動で行う。作り直すときは、リフレッシュトークンも新しくする（ローテーション）。
- Cookie の `HttpOnly` を付けると、JavaScript からトークンを読めなくなり、XSS で盗まれにくくなる。
- 秘密鍵は、ログインのたびやサーバー起動のたびに作るものではない。起動のたびに作ると、再起動で全員のトークンが無効になり、サーバーごとに鍵が違って他のサーバーが確かめられなくなる。
- このアプリの秘密鍵：環境変数 `JWT_SECRET` から読む（`application.properties`）。開発では Git に書かれた開発用の値を使っているので、本番では長いランダムな値を新しく作って設定する。
- 認証 ＝ 相手が誰かを確かめること。認可 ＝ その人が何をしてよいかを決めること（例：自分の投稿だけ削除できる）。
- AWS の IAM のアクセスキー・シークレットキーは、開発者が AWS を操作するためのもので、JWT の秘密鍵とは関係ない。
- このアプリの EC2 は今1台。複数台にするのは将来の拡張（Auto Scaling）。
