# Q10. DTOパターン

## 問題

エンティティを直接APIに使わない理由を説明してください。

## 回答

エンティティはデータベースに保存する形であり、ユーザーの情報などがそのまま入っているものです。そのため、APIからリクエストが来た際に、直接エンティティの形で返すと、不必要な情報まで渡してしまうことになります。そうすると、特にハッシュ化したパスワードやメールアドレスが届いてしまい、第三者から悪用されてしまう危険性があります。例えば、メールアドレスには迷惑メールが届くようになり、パスワードのハッシュ値からは、その値になるパスワードを総当たりで見つけ出されて、不正ログインされるおそれがあります。

そのため、エンティティから必要な情報のみを渡すことができるDTOを挟むことで、リクエストに沿った必要な情報のみをレスポンスすることができます。

また、エンティティの内容を変えた場合でも、DTOへの詰め方を変更内容に沿って直すだけで、APIには変わらない形でレスポンスがされるため、データベースの変更の際にも変更するところが少なくて済みます。

## 理解のメモ

- 流れ：受け取るとき「リクエスト → DTO → エンティティ → DB」、返すとき「DB → エンティティ → DTO → レスポンス（JSON）」。
- たとえ：DTO はレストランのメニュー表。厨房で食材の呼び方が変わっても、お客さんに見せるメニュー表は同じなので、お客さんは困らない。
- このアプリの例：エンティティ `User` には `email`・`passwordHash`・`bio`・`createdAt` などがあるが、投稿者として返す `UserDto` は `id`・`username`・`displayName`・`avatarUrl` だけ。`avatarKey`（画像の保存場所）は、DTO では `avatarUrl`（画像の URL）に変えて返す。
- このアプリでは、メールアドレスはログインの ID でもある。知られると、あとはパスワードを当てればよい状態になる。
- ハッシュ値をそのままパスワード欄に入れても、サーバーがもう一度ハッシュ化して比べるので、ログインできない。攻撃者は、自分のパソコンの中で総当たりを何億回も試す。ログイン画面のレート制限にはかからないので、BCrypt のストレッチング（Q3）で遅くする。
- DB の列名を `display_name` から `nickname` に変えても、DTO で `user.getNickname()` を `displayName` に詰めれば、JSON は `{"displayName": ...}` のまま。エンティティをそのまま返すと JSON の名前も変わり、画面やスマホアプリで名前が空欄になる。
- 受け取る側でも DTO を使う。エンティティで直接受け取ると、利用者が `passwordHash` や `id` を JSON に勝手に足して送り、書き換えられてしまうおそれがある。DTO で受け取れば、決めた項目しか入らない（例：`SignupRequest`）。
- 用途ごとに DTO を分けられる。投稿者の表示は `UserDto`、フォロー一覧は `followedByMe` なども持つ `UserSummaryDto`。
- DTO は Data Transfer Object（データを運ぶための入れ物）の略。
