# Q2. アクセストークンとリフレッシュトークン

## 問題

以下について説明してください：

- なぜトークンを2種類に分けるのか
- アクセストークンの有効期限が短い理由

（アクセストークン: 15分 / リフレッシュトークン: 7日）

## 回答

アクセストークンは、ブラウザにのみ保持されるため、サーバーに記録がありません。よって、第三者に複製された場合には、アクセストークンの有効期限が切れるまで悪用を防ぐことができません。それを防ぐため、アクセストークンの有効期限を15分と短く設定する必要があります。

しかし、そうした場合に15分でログイン状態が解除されてしまうため、ユーザビリティが損なわれてしまう恐れがあります。

また、リフレッシュトークンはサーバーのデータベースにも記録されるため、第三者に複製された場合であっても、サーバーの方で無効にしてしまえば、第三者からの認証を防ぐことができます。ただし、リフレッシュトークンのみにすると、リクエストのたびにデータベースへ通信するので、データベースへの負荷が多くなります。

よって、アクセストークンの有効期限を15分と短くし、さらにリフレッシュトークンを7日という長い期間で設定することによって、普段はアクセストークンのみのリクエストで認証し、リフレッシュトークンの役割でユーザビリティを損なわないようにするというような、両方を用いた認証システムを採用することが大事となってきます。

## 理解のメモ

- 1種類だけにすると、どれも困る。
  - アクセストークンだけで7日：盗まれると最大7日間悪用される。サーバーに記録がないので途中で止められない。
  - アクセストークンだけで15分：15分ごとにログインし直しになる。
  - リフレッシュトークンだけ：実質セッション認証と同じ。すぐ無効にできるが、リクエストのたびに DB へ問い合わせるので、DB の負担が増え、応答も遅くなる。7日間使える値を毎回送るので、盗まれる機会も増える。
- 2つの違いは「ブラウザにあるか」ではなく「サーバー側にも記録があるか」。どちらもブラウザの Cookie に入っている。
- サーバーは、他人の手元にあるトークンを消しに行けない。できるのは、自分が持っている記録を無効にすることだけ。
- アクセストークンの確認は、署名と有効期限だけで行い、DB を見ない（投稿の取得などの処理では DB を使う）。
- Cookie の送り先も違う。`access_token` は `Path=/`（すべての API に送る）、`refresh_token` は `Path=/api/auth`（登録・ログイン・再発行・ログアウトなどにだけ送る）。長く使えるものほど、送る範囲を絞っている。
- ログアウトすると、ブラウザの Cookie は削除され、DB のリフレッシュトークンは失効（無効化）する。行は消さず `revoked_at` に日時を入れる。
- リフレッシュトークンを無効にしても、複製されたアクセストークンは有効期限（最大15分）まで使える。止められるのは、その先の再発行。
- 盗用の検知：失効済みのリフレッシュトークンが使われたら、盗用とみなして同じ系列（`family_id`）をすべて失効させる（失効から30秒以内の再利用は、複数タブの同時リフレッシュとみなして 401 を返すだけ）。
