# Q11. グローバル例外ハンドリング

## 問題

各Controllerでtry-catchする場合と比較した利点を説明してください。

## 回答

各Controllerでtry-catchする場合は、Controllerごとに、エラーをどのように返すかを書かなければいけません。それに対し、グローバル例外ハンドリングは、Webアプリケーションの中で共通のエラーを返すコードを1か所に書きます。そのため、書くコードが少なく済み、漏れも少なくなります。

また、エラーのJSONの形が共通になるため、画面（React）の側で読み間違えることもありません。Controllerごとに書くと、開発者によって形がばらばらになり、画面がエラーのメッセージを見つけられなくなってしまいます。

さらに、想定していなかった例外が発生した場合には、決まった例外への対応しかないtry-catchと違い、エラーが発生したことをユーザーに伝えることができます。その際、「エラーが発生しました」だけを返して詳しい内容を伝えないことにより、渡してはいけない情報を渡すことがないので、第三者への悪用リスクも減らせます。

## 理解のメモ

- 例外 ＝ 処理を続けられないときに投げる「札」。投げると、その処理はそこで止まる。try-catch ＝ 「この処理を試して（try）、札が飛んできたら受け止めて（catch）、こう対応する」と書くコード。設定ではなく、開発者が書く処理。
- このアプリのバックエンドが返すのは、エラーページではなく JSON：`{ "error": { "code", "message", "details" } }`。画面にどう出すかは React が決める。
- React の側は、バックエンドの JSON を作り直せない。形がばらばらだと、形ごとに読み方を書き分けるしかない。だから形をそろえるのは、バックエンドの仕事。
- 理由を伏せるのは、想定していなかった例外のときだけ。他人の投稿の操作（403「この操作は許可されていません」）や入力の誤り（400）では、理由を伝える。
- 想定していなかった例外を誰も受け止めないと、Spring Boot が自分の形（`timestamp`・`status`・`error`・`path`）で 500 を返す。アプリで決めた形と違うので画面は読めず、ログを残すコードもなければ、開発者が気づけない。
- 詳しい内容（DB のサーバーの住所、DB のユーザー名、プログラムの場所など）は、攻撃者の手がかりになる。利用者には返さず、サーバーのログにだけ残す。Q10 の「必要な情報だけを返す」と同じ考え方。
- Controller には、受け取って Service に渡す本来の仕事だけが残り、読みやすくなる（Q9）。
- このアプリの実装：`GlobalExceptionHandler` に `@RestControllerAdvice` を付けると、すべての Controller の例外を受け止める。Service は `ApiException.forbidden()` などを投げるだけで、`handleApi` が共通の JSON にする。一番下の `@ExceptionHandler(Exception.class)` が、想定していなかった例外をすべて受け止め、ログに残して 500「エラーが発生しました」を返す。
- try-catch がまったく要らないわけではない。その場で対応できる例外は、その場で受け止める（例：`PostController` で日時の形式が読めなければ、その場で 400 の札に変える）。
