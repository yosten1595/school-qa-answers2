# Q15. Axiosインターセプター

## 問題

インターセプターとは何か説明してください。

また、これが無い場合の問題点も述べてください。

## 回答

Axiosのインターセプターとは、リクエストの送信前と、レスポンスの受信後に、共通の処理を施すことを言います。例としては、リクエストのヘッダーにアクセストークンを追加したり、レスポンスの受信後のエラー処理を共通で作成しておいたりすることができます。

これが無い場合、開発者は、トークンを追加するときやエラー処理を作成するときに、一つ一つ行わなければいけません。そうすると、コードの間違った入力のほか、付け忘れなどのミスが起きやすくなってしまいます。また、機能を追加した場合に、他の機能と同じ設定をしたい時に忘れる恐れがあります。例えば、新しく作った機能だけ、アクセストークンの有効期限が切れたときの処理を書き忘れると、その機能だけ認証されず、ログインが切れたように見えてしまいます。そのため、そのような処理は一元化しておいた方がいいです。

## 理解のメモ

- 読み方は「アクシオス」。interceptor は「途中で受け止めるもの」。リクエストとレスポンスが通る道の途中に置く、共通の関所のようなもの。
- 書き方の例（Axios）：`api.interceptors.request.use(config => { ...; return config; })` で送信前、`api.interceptors.response.use(res => res, error => { ... })` で受信後の処理を1か所に書く。
- 例：ログインから20分後に「いいね」を押す。アクセストークン（15分）は切れているので、サーバーは 401 を返す（リクエストは届いている）。共通の処理があれば、自動でリフレッシュして、もう一度送る。書き忘れた画面だけ、いいねが付かず、ログインが切れたように見える。リフレッシュトークン（7日）はまだ使えるのに。ほかの画面は動くので、開発者も気づきにくい（Q2）。
- リクエストは、①1行目（メソッドと URL）②ヘッダー ③ボディ（本文）の3つでできている。ヘッダーは「名前: 値」の形で、中身についての情報を並べたもの（たとえ：封筒の表書き。ボディは中の手紙）。例：`Content-Type`（ボディの形）、`Cookie`、`Authorization`（`Bearer` + トークン）、`User-Agent`。レスポンスにもヘッダーがある（`Set-Cookie`、CORS の `Access-Control-Allow-Origin` など）。
- 「ヘッダーにアクセストークンを追加する」は、多くのアプリで、インターセプターが `Authorization` ヘッダーにトークンを自動で書き込むこと。
- トークンを作るのはサーバー（Q1）。画面の側は、受け取ったトークンを付けて送るだけ。
- Q11 のグローバル例外ハンドリングと同じ考え方。バックエンドではエラーを1か所で JSON にし、フロントエンドでは API の呼び出しを1か所にまとめる。
- このアプリは Axios ではなく、ブラウザに最初からある `fetch` を使っている。`frontend/src/api.ts` の `request` 関数に、インターセプターと同じ役割をさせている（「各画面から直接 fetch しない」）。401 ならリフレッシュして1回だけ再送する、複数の 401 が同時に来てもリフレッシュは1回にまとめる、エラーの JSON を `ApiError` に変える、5xx を報告する、をここで行う。
- このアプリでは、アクセストークンをヘッダーに追加する処理はない。トークンは HttpOnly の Cookie に入っていて、JavaScript からは読めない（Q7）。そのかわり、ブラウザが Cookie を自動で付けて送る。
