# Q5. CORS設定の実務理解

## 問題

以下について説明してください：

- 本番環境でのCORS設定の変更点
- `allowedOrigins("*")`の問題点

## 回答

CORSであらかじめ許可したいオリジンを設定しておくことにより、自分が見せてもいい相手のみ許可することができ、第三者からの悪用を防ぐことができます。ブラウザは、CORSの設定を見て、受け取った応答を画面に渡すかどうかを判断します。

本番環境では、開発環境で作成したオリジンを、暗号化されたHTTPSのルールで、ホストをドメイン名として作成したオリジンに変えます。開発のリストのまま本番に出した場合、画面のオリジンは本番のものなのに、CORSで許可されているオリジンは開発のものであるため、許可されておらず、APIから取ってくる中身が出なくなってしまいます。また、本番環境では開発用のオリジンを使わなくなるため、開発用のオリジンは許可しないこととします。

`allowedOrigins("*")` とするときの問題点は、CORSの設定で許可を出す範囲が、すべてのオリジンとなるため、不特定多数のサイトから見られることにより、第三者からの悪用のリスクが高まることです。

## 理解のメモ

- 読み方は「コルス」。Cross-Origin Resource Sharing の略。
- たとえ：ブラウザは太郎さんの秘書、CORS の設定は「見せてよい相手のリスト」、相手の住所がオリジン、社員証が Cookie などの認証情報。秘書は、リストに載っていない相手には、受け取った情報を見せない。
- リストは利用者（太郎さん）を守るためにある。リストを作るのはサーバー、見て判断するのはブラウザ。
- リストに載せるのは人ではなく、オリジン（プロトコル・ホスト名・ポート番号の組み合わせ）。
- リストは人が書いたものなので、本番に出しても自動では変わらない。変わるのは画面の住所のほう。秘書は「画面の住所」と「リストの住所」を見比べ、違えば渡さない。
- 開発のリストのまま本番に出すと、情報が漏れるというより、本物の画面にも中身が渡らず、アプリが動かなくなる。
- `localhost` は利用者それぞれの自分の PC を指す。本番のリストに残すと、利用者の PC の 5173 番で動く、アプリと無関係なページにも情報が渡りうる。要らない相手はリストに残さない。
- `*` は「誰にでも見せてよい」。ただし Cookie などの認証情報付きのリクエストでは、ブラウザは `*` を認めない。だから `*` では、(1) 認証情報なしで取れる情報がどんなサイトにも渡り、(2) 別オリジンの画面から Cookie でログインして使うアプリは正しく動かない。相手の住所をはっきり書く。
- CORS はログインの代わりではない。また、ブラウザを通さない `curl` などには効かない。
- このアプリは、画面と API を同じオリジンで提供するので、CORS の設定自体がない（開発は Vite の `proxy`、本番は nginx が中継。NFR-SEC-11）。
